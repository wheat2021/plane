## Context

当前编辑器在图表能力上只有 `mermaidBlock`，`drawioBlock` 需要同时覆盖三类需求：

1. 交互层：显式按钮切换（编辑/预览/源代码），避免依赖编辑器全局状态或隐式事件。
2. 存储层：draw.io XML 体积大，页面 HTML 不应直接承载完整 XML，需要外置资产化。
3. 基础设施层：默认使用内网 draw.io 服务，支持本地开发与生产反向代理一致路径。

现有仓库已具备可复用基础：

- TipTap 自定义节点扩展体系（`mermaidBlock`、`custom-image`）
- 统一 `FileAsset + MinIO` 资产上传/恢复/复制能力
- `compose` + `proxy` 的服务编排与统一入口

约束条件：

- 仅允许 `mxfile`，不接受裸 `mxGraphModel`
- 不做自动同步，全部手工触发
- 不引入“drawio 地址可配置”能力，默认内网服务

## Goals / Non-Goals

**Goals:**

- 在编辑器中提供 `drawioBlock` 三模式能力，并保持切换行为可预期
- 通过手工同步实现“图形编辑器内容 ↔ 源码 XML ↔ 预览图形”一致性
- 将 draw.io XML 外置到资产系统，降低文档体积与协同更新噪音
- 将 draw.io 服务纳入项目部署编排，默认走内网服务路径
- 保持复制/删除/恢复等资产生命周期与现有编辑器一致

**Non-Goals:**

- 不引入 draw.io 实时协同编辑（多人同图实时操作）
- 不支持 `mxfile` 以外格式作为源码输入
- 不在本次改造中提供用户级 draw.io 地址配置或多租户 draw.io 路由策略
- 不修改历史文档中的非 drawio 图表节点行为（除已定义的 mermaid 交互规范对齐）

## Decisions

### 决策 1：采用 `drawioBlock` 独立节点，而不是复用 `codeBlock`

**选择**：新增独立 TipTap 节点 `drawioBlock`，HTML 标识为 `pre[data-type="drawioBlock"]`。

**理由**：

- 需要承载三模式工具栏、全屏 Modal、iframe 通信状态，远超普通 `codeBlock` 语义
- 可复用 `mermaidBlock` 的扩展模式，降低理解与维护成本
- 能在 `codeBlock` 解析链路中显式避让 `drawio` fence，减少冲突

**备选方案**：在 `codeBlock(language=drawio)` 上做分支渲染。  
**放弃原因**：会把复杂状态塞入通用代码块分支，后续上游同步冲突风险更高。

### 决策 2：三模式全部显式切换，默认进入“源代码”

**选择**：按钮固定为 `编辑`、`预览`、`源代码`；切换行为仅由按钮触发。

**理由**：

- 与用户要求一致，规避 mermaid 早期“隐式状态驱动”踩坑
- 模式语义清晰，避免用户在编辑器可编辑/只读切换时出现图形状态误判

**备选方案**：根据 `editor.isEditable` 自动决定代码/预览。  
**放弃原因**：状态不可见且不可控，历史上已验证易出现误触发与同步歧义。

### 决策 3：编辑模式使用全屏 Modal + iframe 嵌入 draw.io

**选择**：`编辑`按钮打开全屏 Modal，内部 iframe 加载内网 draw.io，使用 `postMessage` JSON 协议。

**理由**：

- draw.io 原生交互复杂，全屏可避免在富文本容器内适配大量布局问题
- 官方 embed 协议成熟，支持 `init/load/save/exit/export/autosave` 事件

**备选方案**：内联嵌入编辑器。  
**放弃原因**：在文档流中会显著破坏排版与滚动体验，且工具栏空间不足。

### 决策 4：XML 存储复用 `FileAsset + MinIO`，文档仅存 `asset_id`

**选择**：`drawioBlock` 节点属性持有 `src`（`asset_id`）与必要元信息，XML 本体存 MinIO。

**理由**：

- 与现有图片资产链路一致，天然具备上传、复制、恢复、删除能力
- 避免页面 HTML 膨胀与协同编辑高频大文本同步开销
- 无需新增数据库对象模型和独立权限体系

**备选方案**：新增数据库表存 XML。  
**放弃原因**：实现成本高、重复建设生命周期能力、数据库膨胀风险大。

### 决策 5：后端按 `entity_type` 放开 XML MIME，并增加原文读取接口

**选择**：在描述类资产上传路径允许 `text/xml`/`application/xml`，并提供权限受控 XML 文本读取能力。

**理由**：

- 当前 `assets/v2` 上传白名单偏图片，不能直接承载 drawio XML
- 前端源码模式需要直接拿 XML 文本，不应依赖跨域重定向下载 URL

**备选方案**：前端直接 fetch MinIO 预签名下载地址。  
**放弃原因**：依赖浏览器跨域/重定向行为，稳定性与安全策略不可控。

### 决策 6：默认内网 draw.io 服务，统一 `/drawio` 路径

**选择**：开发与生产都新增 draw.io 容器，并通过反向代理挂载统一路径（建议 `/drawio`）。

**理由**：

- 避免硬编码公网 `embed.diagrams.net`
- 同源路径可降低 iframe 通信与安全策略复杂度

**备选方案**：直接访问容器裸端口。  
**放弃原因**：环境切换成本高，不利于生产与开发一致性。

## Risks / Trade-offs

- **[风险] 上游同步冲突集中在 editor 核心文件** → 采用“新增目录 + 最小追加修改”策略，并在任务中单独标记高风险文件。
- **[风险] draw.io iframe 消息处理被恶意消息污染** → 严格校验 `origin` 与 `source`，仅接受白名单消息结构。
- **[风险] XML 内容损坏导致预览失败** → `mxfile` 结构校验 + 错误提示 + 保留源码回退入口。
- **[风险] 资产外置后复制页面可能丢图** → 扩展资产提取/替换逻辑，将 `drawioBlock` 纳入复制链路。
- **[权衡] 手工同步降低自动化程度** → 换取更可控的编辑语义和更低误同步概率。

## Migration Plan

1. 先上线后端资产能力（XML MIME、原文读取接口）与基础设施（drawio 容器、代理路径）。
2. 再上线前端 `drawioBlock` 节点与三模式 UI，默认对新节点生效。
3. 补齐资产生命周期与复制链路扩展，确保页面复制/删除行为一致。
4. 通过 feature flag（如需要）灰度启用，验证稳定后全量开放。

**回滚策略**：

- 前端回滚：移除 `drawioBlock` 注册与 slash command，旧文档中的 `drawioBlock` 按普通代码块降级展示。
- 后端回滚：保留已上传资产对象，不删除历史 `FileAsset` 记录，仅关闭入口与读取接口。
