# 部署模式

> 原文: https://docs.warp.dev/agent-platform/cloud-agents/deployment-patterns

团队以几种可重复的方式采用 Cloud Agent。本文介绍最常见的架构、适用场景及其组合方式。

## 心智模型

Oz Cloud Agent 设置通常有四个关键部分：

1. **触发器（Trigger）**：某事发生（CI 步骤、webhook、cron、Slack @提及）
2. **编排（Orchestration）**：决定运行什么并追踪状态（Oz 编排器、GitHub Actions、你的内部系统）
3. **执行（Execution）**：代理实际运行的地方（你的 runner、Oz 托管环境、自托管 worker）
4. **可见性（Visibility）**：团队如何监控和干预（Oz 仪表盘、会话共享、API）

---

## 模式 1：纯 CLI 代理（自带编排器）

适合已有调度工作系统（CI、开发机、内部编排器）的团队，只需一个可靠的云端连接代理运行器。

### 架构

- **触发器**：GitHub Actions / CI、脚本、开发机操作或内部编排器
- **编排**：你现有的系统
- **执行**：该系统运行的地方
- **Warp 提供**：云端连接、共享上下文、可见性、会话共享和追踪

### 团队选择此模式的原因

- 希望**即插即用替代**其他 CLI/SDK 代理（Claude Code、Codex CLI 等）
- 希望在任何地方运行代理，无需 Warp 桌面应用
- 即使执行在"Warp 之外"，仍需**团队级可观测性**

### 常见示例

- **CI PR 助手**：运行格式检查、生成审查评论、建议修复、提交 PR
- **远程开发机代理**：在预配置的开发机中运行重构或调试任务
- **内部编排器集成**：将 Warp 作为多个模型提供商之一的代理选项

### 无 Warp 编排仍可获得的能力

- 访问共享的 Warp 上下文（如 MCP 配置、Warp Drive 上下文、规则/prompt）
- Agent Session Sharing 监控/引导运行
- 用于追踪和报告的只读 API
- "交接"工作流的路径（运行可在更丰富的界面中继续或检查）

### 最小配置清单

- Warp 团队
- 服务账号（推荐用于自动化）
- 在 runner/开发机上安装 Oz CLI
- 所需凭证（通常通过密钥 + 环境变量）

## 模式 2：Oz 托管代理 + Oz 编排（托管云执行）

适合希望 Oz 在 Warp 管理的基础设施上运行代理工作负载的团队，通常在可重现的 Docker 环境中运行。

### 架构

- **触发器**：第一方集成、cron 定时、API/SDK 调用或按需命令
- **编排**：Oz 编排器
- **执行**：Oz 托管环境（基于 Docker）
- **可见性**：Oz 仪表盘 + 会话共享 + API/SDK

### 团队选择此模式的原因

- 希望以最简单的路径实现可重现、可扩展的云端执行
- 需要并行运行大量任务，无需自建沙箱和扩展层
- 需要具有标准化环境和集中配置的一致"生产"设置

### 常见触发方式

- **第一方集成**（Slack、Linear 等）：从外部事件自动创建任务
- **定时代理**：用于循环工作（类 cron 自动化）
- **自定义触发器**：使用 Warp API/SDK 从你自己的系统触发
- **按需云任务**：使用 `oz agent run-cloud` 命令

### 实践示例：每日死代码清理

1. 定义包含仓库和工具链的 Oz Environment
2. 创建带有固定 prompt 的定时任务
3. Oz 按节奏运行代理
4. 团队在 Oz 仪表盘中监控运行，审查产出（PR、计划），必要时介入

### 实践示例：扇出并行工作（分片）

如果任务可自然分割：

- 通过 `oz agent run-cloud` 启动多个代理，每个带有：
  - 仓库的一个分片（目录/模块负责范围）
  - prompt 的一个分片（一个职责）
- 在你偏好的系统中聚合结果（PR、笔记、计划）

### 实践示例：同一任务跨多模型

- 以相同 prompt 启动 N 个运行，但使用不同 profile 映射到不同模型
- 比较结果并选择最佳输出（或合并）

## 模式 3：自托管执行

适合需要执行和代码保留在网络边界内，但仍希望使用 Oz 编排和可见性的团队。

> **企业功能**：自托管执行仅对 Enterprise 计划的团队开放。

### 架构

- **触发器**：与其他模式相同（集成、定时、CLI、API/SDK）
- **编排**：Oz 编排器
- **执行**：你的基础设施，运行自托管 worker
- **可见性**：与 Oz 托管相同的仪表盘、会话共享和 API

### 团队选择此模式的原因

- 需要代码和执行保留在网络边界内
- 有合规或安全要求，不能使用 Warp 托管计算
- 希望使用自有基础设施同时享受 Oz 编排能力

### 工作方式

1. 在你的基础设施上运行一个连接到 Oz 的 worker 进程
2. 使用 `--host "your-worker-id"` 创建任务时，Oz 将其路由到你的 worker
3. Worker 本地运行任务并向 Oz 报告状态
4. 团队获得与 Oz 托管运行相同的可观测性
